5. Friction I would ask about

Ordered by how much I suspect they matter. These are the questions, not conclusions.

1. The note is generated once and then goes inert.

This is the big one. Notes are the entry point to the whole app — material comes in here first — but a finished note has no path onward. To quiz yourself on it you go to the Quizzes hub and paste the source material again. Nothing links a quiz, an exam or a planner task back to the note it came from; StoredNote and StoredQuiz share only a subjectId.
Ask: should the note be the hub — “generate flashcards from this note” inline — and should generated artefacts carry a sourceNoteId?

2. Pull-to-refresh currently does nothing.

The gesture is fully built — damping, thresholds, a success state reading “Note Refreshed with ተማሪ AI”. The handler passed in is await new Promise(r => setTimeout(r, 850)). It waits, then claims success. The note is unchanged.
Ask: wire it to real re-generation, or remove it? Shipping a gesture that lies about having done work is worse than not having it.

3. Two gestures share one pointer surface.

Long-press-to-explain and pull-to-refresh both listen on overlapping elements. A slow downward drag starting on a word begins a press timer and a pull. The 8px drift cancel is what keeps them apart.
Ask: does this hold up on a real touchscreen? I could not verify — no browser in this environment.

4. Markdown is rendered by regex into raw HTML.

formatMarkdown is ~90 lines of chained .replace() feeding dangerouslySetInnerHTML. No sanitiser. Model output is trusted today, but the same path renders pasted user material. Nested lists, code blocks and inline links are unsupported.
Ask: worth moving to a real parser, or is the constrained subset a feature?

5. Editing is a raw markdown textarea.

Editing replaces the reading pane with a 16-row monospace box — no preview, no split view. The learner leaves the rendered note to edit the note. Ask: live preview, or edit-in-place on the rendered surface?

6. Smaller things.
  • Delete uses window.confirm — an OS dialog in an otherwise fully styled app. Not unique to Notes: there are 5 across the codebase (Notes, Quizzes, Exams, Analytics, and exam submit).
  • Search is exact-substring, so “mitochondria” misses “mitochondrion”.
  • No sort or filter control; list order is store order.
  • Long generations cannot be cancelled — AbortError is handled in the port but nothing surfaces it.
  • The list rail has a fixed 600px scroll area independent of the viewer's height.

6. What I would most like advice on

  1. Should the note become the workspace — quizzes, exams and tasks spawned from it and linked back — or stay a document, with the hubs as peers?
  2. Is a two-pane list+reader right at this scale, or does it cost too much width once notes get long? The reader is 8 of 12 columns.
  3. Are the gestures pulling their weight? Long-press-to-explain is genuinely useful. Pull-to-refresh is a stub. Both cost complexity on a surface whose main job is reading.
  4. Where should “generate” live? It is currently a modal over the hub. If notes are the entry point to the app, a full-page intake might carry the weight better.
